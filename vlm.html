레시픽

요리 영상을 단계별 레시피로 바꾸는 서비스

2026.10.06–2026.11.18

프로젝트 개요

레시픽은 요리 과정을 촬영해 올리면 영상을 ‘양파 볶기’, ‘소스 넣기’ 같은 단계로 나누고, 각 단계의 시작·종료 시각과 이름을 제안하는 기록 앱입니다. 사용자는 영상과 분석 결과를 대조하며 잘못 나뉜 구간과 이름을 고치고, 완성한 레시피를 카드로 저장하거나 공유할 수 있습니다.

프로젝트는 조리 로봇의 학습에 쓸 영상에서 동작 구간을 표시하는 기업 과제로 시작했습니다. 팀은 사람이 일일이 구간을 찾는 작업을 줄이기 위해 영상 분석을 실험했고, 사용자가 레시피를 만들며 고친 단계와 학습에 동의한 영상을 수집할 수 있도록 서비스로 확장했습니다.

기업 과제
조리 영상의 동작 구간 경계 검출 파이프라인 개발
담당
VLM에 보낼 장면 선별과 판독 비교, 사람 단계 라벨 구축, 평가 코드 작성
주요 기술
Python, 시각언어모델(VLM), Qwen3.5-27B, LoRA, Expo/React Native

촬영한 영상이 레시피가 되기까지

사용자가 앱이나 웹에서 영상을 선택하면 업로드·분석 서버가 요청을 받습니다. GPU에서 실행하는 시각언어모델이 영상에서 시간순으로 뽑은 이미지 묶음을 읽어 어떤 재료를 사용하고 어떤 동작을 하는지 파악합니다. 이어서 장면을 조리 단계로 묶고 각 구간에 한국어 이름을 붙입니다.

분석 결과가 돌아오면 사용자는 단계별 영상과 시각을 확인하고 결과를 수정할 수 있습니다. 앱 서버는 레시피 기록, 단계 수정 이력, 학습 활용 동의·철회 이력을 저장합니다. 수정한 단계는 사람 검수 후보로 남고, 로봇 학습용 영상은 동의한 경우에만 수집할 수 있게 설계했습니다.

영상에서 조리 동작의 경계 찾기

처음에는 영상의 색 분포나 연속 프레임의 차이가 크게 바뀌는 곳을 찾았습니다. 재료를 넣거나 소스를 부을 때는 변화가 나타났지만, 비슷한 색의 재료를 뒤집거나 소량의 양념을 넣을 때는 놓치는 경우가 있었습니다. 팀은 사람 검수 영상 32편에서 색·움직임 특징, 영상 임베딩과 변화점 탐지 등 59가지 방법을 비교했습니다. Gemma 임베딩과 KTS의 조합을 주요 기준선으로 삼았고, 소량 투입은 여러 방법에서 계속 탐지하기 어려웠습니다.

  1. S1. 변화 후보 검출영상 특징을 비교해 동작이 달라졌을 만한 시각을 찾습니다.
  2. S2. 프레임 선별후보 주변을 촘촘히 보고 후보 사이에도 확인할 장면을 배치합니다.
  3. S3. VLM 판독선별한 장면을 시간순으로 묶어 재료와 조리 동작을 읽습니다.
  4. S4. 단계 확정이어지는 판독 결과를 작업 단위로 묶고 단계가 바뀌는 시각을 정합니다.

내가 맡은 실험과 평가

저는 변화 후보를 받은 뒤 어떤 장면을 모델에 보여 줄지, 모델이 읽은 장면을 어디서 나눌지, 그 결과를 어떤 기준으로 평가할지를 맡았습니다.

놓치는 단계가 늘지 않도록 판독할 장면 줄이기

변화 후보 전후 2초는 더 자주 읽고, 후보가 없는 곳은 8초마다 보완 장면을 넣는 조건을 설계했습니다. 공통 입력·실행·평가 코드를 작성하고 8편을 직접 실행해 팀원이 실행한 8편과 합쳤습니다. 16편에서 1초마다 한 장을 읽는 기준 방식의 53%에 해당하는 토큰을 사용했습니다. 사람 경계와 ±5초 안에서 일치하는지를 본 F1은 기준 방식 0.674, 선별 방식 0.709로, 실험에서 정한 성능 유지 기준을 충족했습니다.

장면을 봤는데도 경계를 놓치는 이유 확인

선별 방식이 놓친 경계 92개를 확인하니, 64개는 앞뒤 장면을 읽고도 모델이 같은 단계라고 답한 경우였습니다. 이후에는 사람이 하나의 작업으로 보는 범위에 맞춰 답하도록 지시문을 바꿨습니다. 예를 들어 재료를 넣고 여러 번 젓는 장면에서 손이 움직일 때마다 단계를 새로 만드는 문제를 줄이려 했습니다.

사람이 붙인 단계 라벨을 만들고, 예측 경계와 정답 경계를 한 번씩만 짝짓도록 평가 코드를 고쳤습니다. 사람 단계 라벨이 있는 16편에서 작업 단위 지시문과 변화 후보·중간 프레임을 조합해 ±5초 F1 0.558을 얻었습니다. 8초 보완 프레임을 더한 조건과 점수 차이를 구별하기 어려워 더 적은 장면을 쓰는 조합을 연구안으로 제안했습니다. 앞선 토큰 절감 실험과는 정답의 단계 정의가 다릅니다.

호출 한도에서 공개 모델 파인튜닝으로

초기 앱은 영상 한 편을 분석하는 데 Claude를 세 번 호출했습니다. 장면 해석을 큰 모델에 다시 확인하는 실험까지 더해지면서 호출량과 비용이 늘었습니다. 팀은 영상 판독 능력을 자체 GPU에서 추론할 수 있는 공개 모델로 옮기기 위해 Qwen3.5-27B를 파인튜닝했습니다.

Claude Sonnet의 답을 학습 데이터로 만들기

3초마다 뽑은 이미지를 12장씩 묶어 Claude Sonnet에 보내고, 65개 학습 클립의 모범 출력을 만들었습니다. 먼저 재료와 동작을 판독하도록 학습했고, 다음 실험에서는 장면 판독, 조리 단계 묶기, 한국어 단계명 생성을 하나의 LoRA 어댑터로 학습했습니다. 평가 영상 23편은 학습 영상과 겹치지 않게 구성했고, 평가는 사람이 확인한 라벨을 기준으로 했습니다.

학습 전후 비교

재료 적중률 55.0% → 77.5%
팀 영상 16편에서 사람이 재료 라벨을 붙인 시각의 판독 결과를 비교했습니다.
동작 분할 적중률 39.3% → 54.0%
영상 23편에서 20초 이상인 모델 단계의 ¼ 지점과 ¾ 지점이 사람이 정한 같은 단계에 들어오는 비율입니다.

두 수치는 3초 간격 입력으로 평가한 Qwen3.5-27B의 학습 전후 결과입니다. 1인칭 영상에서 재료를 놓치거나, 보이지 않는 재료를 이름에 넣고 서로 다른 작업을 길게 합치는 오류는 남았습니다.

서비스 적용과 최종 결과

최종 앱에는 자체 GPU에서 실행하는 Qwen3.5-27B FP8 기본 모델을 연결했습니다. 앱은 1초 간격으로 장면을 뽑고, 긴 영상은 여러 조각으로 나눠 병렬로 판독합니다. 팀은 11월 14일 운영 검증에서 영상 업로드, 분석 결과의 단계 저장, 게시·다운로드 흐름을 확인했습니다. LoRA 어댑터의 학습 결과는 앞의 3초 간격 실험에서 검증했습니다.

11월 18일 최종 발표에서는 영상 한 편이 편집 가능한 조리 단계와 공유용 레시피로 바뀌는 흐름을 소개했습니다. 사용자 수정과 동의한 영상을 다음 검수 데이터로 수집할 구조까지 구현했습니다. 수집된 데이터를 이용한 재학습은 후속 범위로 남았습니다.
