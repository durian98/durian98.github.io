작업 방식

01

구현 전에 가설부터 확인

작업을 맡길 때는 제 가설을 먼저 검토받고, 작은 단위로 바꾼 뒤 변경 내용을 설명하게 합니다. 마지막에는 실패할 수 있는 상황과 그에 맞는 테스트를 제안받습니다. 이 순서를 스킬로 만들어 Claude Code와 Codex에서 같이 씁니다.

learning-first-development · AGENTS.md
02

AI의 답을 근거로 쓰지 않기

AI의 제안 가운데 테스트, 로그, 측정, 공식 문서로 확인한 것만 정리해 둡니다. 단위 테스트 통과를 DB나 배포 환경에서 동작한다는 근거로 쓰지 않는다는 원칙도 지침에 넣었습니다. 설계 검토, 장애 분석, 코드 리뷰에 쓰는 프롬프트는 공개 저장소에 모았습니다.

개인 지침 · 프롬프트 7종
02

프로젝트 사례

01

서브에이전트로 반복 구현 나누기

GABOLLE에서 반복되는 구현은 서브에이전트 두 개에 나눠 맡겼습니다. 각자 다른 폴더와 테스트 DB를 쓰게 해 작업이 섞이지 않게 했고, 핵심 규칙과 통합 테스트는 제가 챙겼습니다. 결과는 변경 내용을 읽고 안전장치를 일부러 빼 테스트가 실패하는지 본 뒤 반영했습니다. 일정 편집 기능에서는 이 과정을 거치며 테스트가 454개에서 519개로 늘었습니다.

Claude Code 서브에이전트 · 격리 테스트 DB
02

AI가 놓친 문제를 사용 흐름으로 찾기

AI가 코드 연결을 점검하고도 놓친 버그 세 개를 실제 사용자처럼 화면을 따라가며 찾았습니다. 그 뒤로는 연결 점검에서 끝내지 않고 실제 사용 흐름까지 확인하도록 작업 규칙을 바꿨습니다.

GABOLLE · 사용자 흐름 점검
03

테스트 설계

AI가 만든 코드일수록 확인 범위를 넓게 잡았습니다. GABOLLE에서는 아래 테스트를 직접 설계하거나 돌려 봤습니다.

  • 단위·슬라이스 테스트
  • 실제 PostgreSQL을 쓰는 통합 테스트
  • 보안 필터까지 거치는 API 테스트
  • k6 부하 시험(로컬)
  • 중복 요청·권한·동시 수정 테스트
  • 작업 프로세스를 강제로 종료하는 복구 시험
  • 안전장치를 하나씩 빼서 테스트가 잡는지 보는 점검
01

통과 숫자 뒤의 빈칸 확인

전체 1,346개 테스트를 돌린 결과를 다시 보니 PostgreSQL 테스트 51개가 조용히 건너뛰어지고 있었습니다. 실제로 실행되도록 바로잡고, 그 뒤로는 건너뛴 테스트 수까지 함께 확인합니다.

JUnit · PostgreSQL · k6

01

참고 자료를 규칙으로 바꾸기

토스 기술 블로그의 디자인 시스템, AI 기반 UI 테스트 자동화, 프롬프트 설계 글을 참고했습니다. GABOLLE에서는 펼쳐지는 하단 시트와 사진 넘김 같은 공통 화면 요소를 AI와 함께 만들었습니다. 이 포트폴리오도 AI와 함께 참고 영상을 프레임 단위로 분석해 움직임의 시간과 곡선을 재고, 그 값으로 컴포넌트를 만들었습니다.
