01

작업 방식

01

구현 전에 가설부터 확인

작업을 맡길 때는 제 가설을 먼저 검토받고, 작은 단위로 바꾼 뒤 변경 내용을 설명하게 합니다. 마지막에는 실패할 수 있는 상황과 그에 맞는 테스트를 제안받습니다. 이 순서를 스킬로 만들어 Claude Code와 Codex에서 같이 씁니다.

learning-first-development · AGENTS.md
02

AI의 답을 근거로 쓰지 않기

AI의 제안 가운데 테스트, 로그, 측정, 공식 문서로 확인한 것만 정리해 둡니다. 단위 테스트 통과를 DB나 배포 환경에서 동작한다는 근거로 쓰지 않는다는 원칙도 지침에 넣었습니다.

개인 지침 · 프롬프트 7종
02

기능 개발

01

계약은 먼저, 반복 구현은 나눠서

GABOLLE의 여행 기록·피드와 동행 초대·공유 API를 만들 때는 테이블, 저장소 인터페이스, 테스트 틀을 먼저 정해 커밋했습니다. 그 위의 업로드 처리와 초대·공유 구현은 서브에이전트 둘에 나눠 맡기고, 각자 다른 폴더와 테스트 DB 스키마를 쓰게 했습니다. 공개 응답에서 개인정보를 빼는 규칙처럼 정책이 걸린 부분은 직접 정하고, 생성된 코드는 변경 내용을 읽고 테스트한 뒤 팀 브랜치에 반영했습니다.

Claude Code 서브에이전트 · Spring Boot · PostgreSQL
02

규칙을 한 곳에 모은 일정 편집

일정 편집은 기존 일정을 고치지 않고 새 판을 쌓는 구조라, 고정·제외·순서 변경·되돌리기가 모두 같은 복사 규칙을 따라야 했습니다. 이 규칙을 한 곳에 모으도록 정하고 AI와 구현했습니다. 안전장치를 하나씩 빼서 테스트가 잡는지 확인하며 테스트를 454개에서 519개로 늘렸습니다.

Spring Boot · JPA · 판(version) 구조
03

화면 공통 요소

펼쳐지는 하단 시트와 사진 넘김처럼 여러 화면에서 쓰는 요소를 AI와 함께 공통 컴포넌트로 만들었습니다.

React Native · Expo
03

성능 개선

01

추천 첫 결과를 기다리는 시간 줄이기

AI와 함께 추천 처리 코드를 분석하고 k6 부하 시나리오를 짜서, 바꾸기 전과 후를 같은 로컬 환경에서 비교했습니다. 첫 코스 응답 p95는 13.5초에서 1.1초로, 시작하지 못한 작업은 27건에서 0건으로 줄었습니다. 운영에는 반영하지 않은 로컬 실험입니다.

k6 · PostgreSQL · 로컬 비교
04

테스트와 검증

AI가 만든 코드일수록 확인 범위를 넓게 잡습니다. GABOLLE에서 직접 설계하거나 돌려 본 테스트입니다.

  • 단위·슬라이스 테스트
  • 실제 PostgreSQL을 쓰는 통합 테스트
  • 보안 필터까지 거치는 API 테스트
  • k6 부하 시험(로컬)
  • 중복 요청·권한·동시 수정 테스트
  • 작업 프로세스를 강제로 종료하는 복구 시험
  • 안전장치를 하나씩 빼서 테스트가 잡는지 보는 점검
01

AI가 놓친 문제를 사용 흐름으로 찾기

AI가 코드 연결을 점검하고도 놓친 버그 세 개를 실제 사용자처럼 화면을 따라가며 찾았습니다. 그 뒤로는 연결 점검에서 끝내지 않고 실제 사용 흐름까지 확인하도록 작업 규칙을 바꿨습니다.

사용자 흐름 점검
02

통과 숫자 뒤의 빈칸 확인

전체 1,346개 테스트 결과를 다시 보니 PostgreSQL 테스트 51개가 조용히 건너뛰어지고 있었습니다. 실제로 실행되도록 바로잡고, 그 뒤로는 건너뛴 테스트 수까지 함께 봅니다.

JUnit · PostgreSQL

참고한 글을 작업에 옮기기

토스 기술 블로그의 디자인 시스템, AI 기반 UI 테스트 자동화, 프롬프트 설계 글을 참고했습니다. 이 포트폴리오도 AI와 함께 참고 영상을 프레임 단위로 분석해 움직임의 시간과 곡선을 재고, 그 값으로 화면을 만들었습니다.

AI 시대에 디자이너로 살아남기 · AI-driven UI 테스트 자동화 · 프롬프트 설계

Jira와 MR 정리, 작업 파일 선점

Jira 티켓 정리와 MR 설명은 코드와 커밋 근거를 확인하게 한 뒤 AI에 맡겼습니다. 여러 사람과 AI 에이전트가 같은 파일을 동시에 고치지 않도록 팀의 MCP 도구로 작업 파일을 먼저 선점했습니다.
